## ⚠ ACHTUNG TIME — ZUERST LESEN (Walter, ABSOLUT, wiederkehrend)

**Bevor du irgendein C#-/DB-Feld mit Datum/Zeit anfasst oder neu anlegst:**

| | Pflicht |
|---|---|
| Schreiben | immer `DateTime.Now` — **nie** `DateTime.UtcNow` |
| PostgreSQL | immer `timestamp without time zone` — **nie** `timestamptz` / `TIMESTAMPTZ` |
| EF-Mapping | `.HasColumnType("timestamp without time zone")` auf jedem `DateTime`-Property |
| Model-Default | `= DateTime.Now` |

Sonst: HTTP 500 beim Speichern (Npgsql lehnt `Kind=Local` auf `timestamptz` ab) — oft nur leeres «Fehler:» im UI. Schon mehrfach passiert (Zusatzadresse, Absenz, Absenz-Typ-Nachrechnung). Checklist auch in `.cursor/rules/achtung-timestamp.mdc`.

**Seit 01.09.2026 prüft der Schema-Wächter das automatisch.** Beim Start vergleicht er bei JEDEM `DateTime`-Property den EF-Typ gegen `information_schema.columns` und schreibt jede Abweichung als Warnung ins Log (`SCHEMA-PRUEFUNG   Zeitzone:  tabelle.spalte ← Model.Property (Datenbank: … / EF: …)`); `/api/instance-info` liefert die Anzahl als `schemaZeitzonen`. Bewusst **nicht** blockierend — es gibt Altbestand, und ob eine Abweichung knallt, hängt davon ab, ob jemand Lokalzeit hineinschreibt. Nach einem Deploy also ins Log schauen: steht dort eine Zeitzonen-Warnung zu einer NEUEN Tabelle, fehlt `.HasColumnType(...)`. (Anlass: `mail_bounce.empfangen_am` — die Spalte existierte, nur der Typ passte nicht, also fiel es der reinen Spaltenprüfung nicht auf und knallte erst beim ersten Rückläufer.)

### Authorization

- JWT Bearer (Secret in `appsettings.json` oder `Jwt:Secret`-EnvVar). Frontend speichert Token in `localStorage.hrToken`.
- Rollen: `admin` (alle Filialen), `superuser` (HR-Verantwortliche), `user` (normaler Benutzer/GF mit Filial-Zugang via `user_branch_access`), `employee` (MA-Postfach-Login — nur eigenes Postfach/Lohnzettel), `buchhaltung` (**wie Superuser + zusätzlich der Fibu-Bereich**, aber filial-beschränkt via `user_branch_access`).
- **Buchhaltungs-Rolle + Fibu-Bereich (Walter-Vorgabe 24.05.2026, präzisiert):** Eigene Rolle `buchhaltung` (kein DB-Constraint auf `app_user.role`, nur neuer String-Wert). **`buchhaltung` = wie `superuser` (volle HR-Feature-Rechte) PLUS der eigene Sidebar-Abschnitt „Buchhaltung → Fibu"** (`page-fibu`, `js/fibu.js`). Inhalt Fibu: **Fibu-Journal** + **Buchhaltungs-Saldo-Liste** — beide aus dem Lohnlauf-Definitiv-Aktionsband (`payroll.js _lohnWfRenderStatusBar`) HIERHER gezogen (Lohnlauf bleibt sauber; GF-Übersicht bleibt im Lohnlauf). **Kontoplan bleibt im Admin** (Systemeinstellungen). Filiale = globaler Sidebar-Selektor (`fixedCompanyProfileId`), Periode = eigene Jahr/Monat-Wahl. PDFs im Vorschaufenster (`previewFileModal`).
  - **Mechanik „wie superuser + fibu" (Doppel-Rollen-Claim):** `AuthController.GenerateToken` gibt einem `buchhaltung`-User ZWEI Rollen-Claims mit: `buchhaltung` (erster Claim) + `superuser`. Damit greifen ALLE `[Authorize(Roles="admin,superuser")]`-Endpunkte automatisch (über den superuser-Claim) — ohne dass Dutzende Attribute angefasst werden müssen. Der `buchhaltung`-Claim schaltet ZUSÄTZLICH die Fibu-Endpunkte frei (`[Authorize(Roles="admin,buchhaltung")]` auf `fibu-journal` + `saldo-liste-buchhaltung` → reine HR/superuser kommen NICHT ins Fibu). Die DB-`role` bleibt `buchhaltung` (für Dropdown/Anzeige; `Me` liefert sie unverändert).

Hinweis: harte serverseitige Filial-Beschränkung greift dort, wo `CanAccessBranchAsync` aufgerufen wird (Fibu, Akonto); in rein superuser-basierten Modulen (Mitarbeiter/Verträge etc.) wirkt v.a. die Selektor-Einschränkung — für eine durchgängige harte Beschränkung müsste man die Branch-Prüfung dort nachrüsten (offen, bei Bedarf).

## Konventionen

- **QuestPDF: Row-Breiten nachrechnen (Bewerbungsbogen-Bug 13.08.2026).** Eine `Row` mit `AutoItem`/`ConstantItem`-Summe > Blattbreite (~495pt bei A4, 1.5cm Rand) wirft zur LAUFZEIT `DocumentLayoutException: conflicting size constraints` — die Meldung nennt KEINE Stelle. Klassiker: zwei lange Frage-Texte + Checkboxen in EINER Zeile, oder Ziffern-Boxen (ConstantItems) in einer zu schmalen RelativeItem-Spalte. Bei solchen Fehlern zuerst Breiten prüfen (Fix: Zeile aufteilen oder Box-Gruppe als `AutoItem`), nicht die Seitenhöhe.

- **NIE geschweifte Klammern in `ExecuteSqlRaw`-SQL (Walter-Crash 13.08.2026, ABSOLUT).** EF Core jagt den SQL-String durch `String.Format` — ein `DEFAULT '{}'` o.ä. wirft zur LAUFZEIT beim Serverstart `FormatException: Expected an ASCII digit` → Startup-Crash/Restart-Loop (Produktion down; konkret: `lse_version.config_json DEFAULT '{}'`). Regel: in Start-Migrations-SQL Klammern entweder als `{{` / `}}` escapen (Muster `slip_json JSONB NOT NULL DEFAULT '{{}}'`) oder den Default weglassen und im EF-Model setzen. JSON-Seeds NIE als Raw-SQL, sondern via EF + `JsonSerializer.Serialize`. Zweite Lehre desselben Vorfalls: **EF-Seeds laufen in DATEIREIHENFOLGE von Program.cs** — ein Seed, der eine Tabelle liest, muss NACH deren `CREATE TABLE`-Block stehen (der LSE-Seed stand davor → «relation does not exist» beim Erst-Start).

- **NIEMALS ein ASCII-`"` (U+0022) innerhalb eines C#-Strings verwenden — wiederkehrender Build-Bug (Walter-Vorgabe 04.07.2026, ABSOLUT).** In deutschen Texten sieht das typografische Paar `„…"` optisch korrekt aus, aber das SCHLIESSENDE Zeichen ist oft ein ASCII-`"` (U+0022) und beendet dann den C#-String vorzeitig → Dutzende Folge-Syntaxfehler (CS1003/CS1002/CS1010 „Zeilenvorschub in Konstante" usw.). **Regel:** in C#-String-Literalen (`"..."`, `$"..."`) für Anführungszeichen um einen Wert IMMER **Guillemets** `«…»` (U+00AB/U+00BB) verwenden — die sind kein String-Delimiter und immer sicher. Beispiel: `$"Typ «{code}» wird verwendet."` — NIE `$"Typ „{code}\" …"`. Gilt für alle Fehlermeldungen, Logs, PDF-/Postfach-Texte. In Kommentaren (`//`) sind die typografischen Zeichen unkritisch (werden nicht geparst). Nach jeder C#-Edit mit deutschem Text kurz prüfen, dass kein blankes `"` mitten im String steht.

- **Personalnummern-Kreis pro Filiale (Walter-Vorgabe 02.09.2026).** Jede Filiale definiert in den Stammdaten ein **Präfix** (z.B. `122`) und eine **Anzahl Stellen** (z.B. `4`) — gültig ist also genau `1220001`–`1229999`. Nummern, die mit **`99`** beginnen, sind alte Archivnummern und zählen NIRGENDS mit. Die zentrale Logik steht in `Services/PersonalnummerKreis.cs` (Klasse `Nummernkreis`) — dort und NUR dort: Präfix normalisieren (`NurZiffern`, ersetzt die früher fünffach kopierte `NormalizeRestaurantPrefix`), `Passt`, `Hoechste`, `Naechste`, `Beanstandung`. Drei Punkte, die man leicht falsch macht:
  1. **Die Personalnummer ist KEIN Schlüssel, sondern ein Infofeld** — OneCrew prüft und meldet, nummeriert aber NIE selbständig um.
  2. **Restaurant-Code ≠ Nummernkreis-Präfix.** Der Restaurant-Code ist ein McDonald's-Stammdatum (CSV-Spalte «Store number»); das Präfix gehört uns. Im CSV-Import werden beide getrennt geführt (`storePrefix` vs. `kreis.Praefix`) — wer sie zusammenlegt, sortiert bei einer abweichenden Filiale die ganze Datei aus.
