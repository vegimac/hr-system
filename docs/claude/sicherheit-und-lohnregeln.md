### Authorization

- JWT Bearer (Secret in `appsettings.json` oder `Jwt:Secret`-EnvVar). Frontend speichert Token in `localStorage.hrToken`.
- Rollen: `admin` (alle Filialen), `superuser` (HR-Verantwortliche), `user` (normaler Benutzer/GF mit Filial-Zugang via `user_branch_access`), `employee` (MA-Postfach-Login — nur eigenes Postfach/Lohnzettel), `buchhaltung` (**wie Superuser + zusätzlich der Fibu-Bereich**, aber filial-beschränkt via `user_branch_access`).
- **Buchhaltungs-Rolle + Fibu-Bereich (Walter-Vorgabe 24.05.2026, präzisiert):** Eigene Rolle `buchhaltung` (kein DB-Constraint auf `app_user.role`, nur neuer String-Wert). **`buchhaltung` = wie `superuser` (volle HR-Feature-Rechte) PLUS der eigene Sidebar-Abschnitt „Buchhaltung → Fibu"** (`page-fibu`, `js/fibu.js`). Inhalt Fibu: **Fibu-Journal** + **Buchhaltungs-Saldo-Liste** — beide aus dem Lohnlauf-Definitiv-Aktionsband (`payroll.js _lohnWfRenderStatusBar`) HIERHER gezogen (Lohnlauf bleibt sauber; GF-Übersicht bleibt im Lohnlauf). **Kontoplan bleibt im Admin** (Systemeinstellungen). Filiale = globaler Sidebar-Selektor (`fixedCompanyProfileId`), Periode = eigene Jahr/Monat-Wahl. PDFs im Vorschaufenster (`previewFileModal`).
  - **Mechanik „wie superuser + fibu" (Doppel-Rollen-Claim):** `AuthController.GenerateToken` gibt einem `buchhaltung`-User ZWEI Rollen-Claims mit: `buchhaltung` (erster Claim) + `superuser`. Damit greifen ALLE `[Authorize(Roles="admin,superuser")]`-Endpunkte automatisch (über den superuser-Claim) — ohne dass Dutzende Attribute angefasst werden müssen. Der `buchhaltung`-Claim schaltet ZUSÄTZLICH die Fibu-Endpunkte frei (`[Authorize(Roles="admin,buchhaltung")]` auf `fibu-journal` + `saldo-liste-buchhaltung` → reine HR/superuser kommen NICHT ins Fibu). Die DB-`role` bleibt `buchhaltung` (für Dropdown/Anzeige; `Me` liefert sie unverändert).
  - **Filial-Beschränkung trotz superuser-Claim:** `PayrollController.CanAccessBranchAsync` prüft den `buchhaltung`-Claim ZUERST → ein buchhaltung-User ist auf seine `user_branch_access`-Filialen beschränkt (NICHT „alle", obwohl er den superuser-Claim hat). `Me` liefert `branches` als Liste (DB-role ≠ admin/superuser) → der Filial-Selektor zeigt nur die zugeteilten. **„alle ausser X"** = die anderen anhaken (Positiv-Liste). **MA-Endpunkte seit 08.10.2026 hart beschränkt:** globaler Filter `MaFilialFilter` (`Services/MaFilialZugriff.cs`, in `AddControllers` registriert) prüft für GF (`user`), `lowuser` und Buchhaltung jeden MA, den eine Aktion anfasst — Parameter `employeeId`/`empId` (Route/Query/Formular), Eigenschaft `EmployeeId` eines übergebenen Objekts, und die Route-Id bei `[MaEintrag(typeof(Eintrag))]` (Bankverbindungen, Absenzen + Ferienkürzung/-auszahlung, Verträge, wiederkehrende Lohnarten, Lohnabtretungen, Verwarnungen, Schwangerschaften, Dokument-Aktionen, `EmployeesController` = MA-Id selbst). Erlaubt = MA hat irgendeine Anstellung in einer eigenen Filiale (auch früher, Übertritt) oder noch keine. Sonst 403 `MA_ANDERE_FILIALE`. **Neuer Controller, dessen `{id}` einen MA-Eintrag meint ⇒ `[MaEintrag(typeof(…))]` setzen** (Klasse, wenn alle `id` denselben Typ meinen, sonst pro Aktion); `[OhneMaFilialPruefung]` nur, wenn die Aktion selbst prüft (Vertrag anlegen: Ziel-Filiale muss eigene sein — Übertritt). Rollen IMMER mit `User.IsInRole(...)` prüfen, NIE `FindFirst(ClaimTypes.Role)` (Buchhaltung hat «buchhaltung» als erste Rolle → so konnte sie sich zum Admin machen). Benutzerverwaltung: Buchhaltung darf nur Benutzer ihrer Filialen anlegen/ändern und keine Rolle admin/superuser vergeben (403 `NUR_EIGENE_FILIALEN`). Tests: `Tests/MaFilialZugriffTests.cs`. Unter-Ids in Routen `api/employees/{employeeId}/…/{id}` IMMER zusammen mit dem MA laden (`x.Id == id && x.EmployeeId == employeeId`) — der Filter prüft nur den MA der Route.
  - **Frontend-Sichtbarkeit:** `startApp` behandelt `buchhaltung` wie HR-Team (`isHrTeam` inkl. buchhaltung → Übersicht/Personal/Finanzen/HR sichtbar) und zeigt zusätzlich `.buchhaltung-section` (admin + buchhaltung). Kein Login-Redirect mehr — buchhaltung landet wie superuser auf dem Dashboard.

Vorher waren u.a. `PayrollController` calculate/confirm/pdf und `EmployeesController` komplett offen. Die MA-Rolle `employee` ist damit standardmässig von ALLEM ausgesperrt.

- **Security-Header (Walter-Vorgabe 23.05.2026):** Middleware ganz am Anfang der Request-Pipeline in `Program.cs` (vor `UseDefaultFiles`/`UseStaticFiles`) setzt auf JEDE Antwort: `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: geolocation=(), microphone=(), camera=()`, `Strict-Transport-Security: max-age=31536000; includeSubDomains`. **Bewusst KEINE Content-Security-Policy** — die SPA nutzt viel Inline-JS/-CSS (`onclick=…`, `<style>`); eine echte CSP braucht erst einen Refactor (Handler auslagern + Nonces).   - **Dezember-Jahresausgleich / Aufrollverfahren (Walter-Vorgabe 20.05.2026):** Die flache Monatsdeckelung `min(basis, 12'350)` gilt für Jan–Nov. Im **Dezember** (`month == 12`) rechnet `PayrollController` die gedeckelten SV (ALV/NBU) auf **Jahresbasis** ab — weil zum Dezemberlohn noch Boni hinzukommen und die flache Deckelung den Bonus sonst fälschlich kappen würde (oder bei tiefen Vormonaten zu wenig verbeitragt). Formel pro gedeckeltem Abzug: `jahresPflichtig = min(Σ(Jan–Nov SvBasisAhv) + Dez-Basis, max_base_monthly×12)`, `bereitsVerbeitragt = Σ min(SvBasisAhv_m, max_base_monthly)`, `Dez-Basis = max(0, jahresPflichtig − bereitsVerbeitragt)`. So zahlt ein Gutverdiener mit Dezember-Bonus exakt auf 148'200/Jahr ALV/NBU. Datenfluss: `Calculate` lädt bei `month==12` die `SvBasisAhv` aller Snapshots Jan–Nov desselben Jahres (über **ALLE Filialen** des MA — Schaub Restaurants GmbH ist EIN AHV-Arbeitgeber; STORNIERTE ausgenommen) als `List<decimal> ytdSvBasesDez` und reicht sie an `BuildResult(... ytdSvBasesDezember)` durch (BuildResult ist `static`, kein eigenes async-DB). `SvBasisAhv` ist UNGEDECKELT gespeichert → dient als Proxy für ALV UND NBU (NBU-Basis ≈ AHV-Basis, separat nicht gespeichert). Die Dezember-ALV/NBU-Zeile wird im Lohnzettel mit Suffix „(Jahresausgleich)" gekennzeichnet. Untergrenze 0, **keine** Obergrenze auf die Dezember-Brutto-Basis (damit über den Monats-Höchstlohn hinaus unterdeckelte Vormonate sauber nachverbeitragt werden; mathematisch ist Dez-Basis stets ≤ 148'200 und ≥ 0). Voraussetzung: Jan–Nov sind als Snapshot definitiv abgeschlossen (sonst zählt der Monat nicht zum YTD). Der Akonto-Lauf braucht keine Anpassung — die flache Akonto-Deckelung wird im Definitivlauf über die Akonto-Verrechnung automatisch korrigiert.
- **Vorschau/Preview persistiert nichts (Walter-Vorgabe 20.05.2026):** `AkontoLaufService.PreviewAsync` ist standardmässig READ-ONLY (`persistLgav=false`) — der LGAV-Auto-Eintrag (LohnZulage Code 140 via `LgavBeitragService.EnsureAsync`) wird NUR in den bewussten Commit-Pfaden geschrieben (`AkontoWorkflowController.Start`, `AkontoController.Commit` → `persistLgav:true`). Reine GET-Vorschauen schreiben nichts. (`EnsureAsync` ist zwar idempotent — max. ein Eintrag pro MA/Jahr —, aber eine Vorschau soll grundsätzlich keine Daten ändern.) - **Optimistic Concurrency (Walter-Vorgabe 20.05.2026):** `payroll_snapshot`, `payroll_saldo`, `payroll_periode`, `akonto_zahlung` haben `UseXminAsConcurrencyToken()` (Postgres-`xmin`, KEIN Schema-Change). Ändern zwei Requests dieselbe Zeile parallel, wirft EF beim 2. `SaveChanges` eine `DbUpdateConcurrencyException`. Ein globales Middleware in `Program.cs` (vor `UseRouting`) fängt die ab und liefert **409 `CONCURRENCY_CONFLICT`** statt 500 — kein still verlorenes Update mehr. Die Kern-Operationen (confirm/akonto-auszahlen/abschliessen) schreiben ihre DB-Änderungen ohnehin in EINEM `SaveChangesAsync` (= implizite Transaktion, atomar); Seiteneffekte (PDF/Postfach/E-Mail) laufen als best-effort `Try*` NACH dem Commit. Beim Bau neuer Bulk-Writes auf diese Tabellen via `ExecuteSqlRaw`/`ExecuteUpdate` beachten: die umgehen den xmin-Check.
- **Audit-Actor immer aus dem Token (Walter-Vorgabe 20.05.2026):** Die handelnde User-ID für Audit-/„abgeschlossen_von"-Felder kommt IMMER aus dem JWT (`User.FindFirst(ClaimTypes.NameIdentifier)`), NIE aus dem Request-Body — sonst könnte sich jeder als jemand anderes ausgeben. `PayrollPeriodeController` hat dafür `GetUserId()` (analog `AkontoWorkflowController.GetUserId()`); `abschliessen` / `definitiv-abschliessen` / `zurueck-an-gf` / `wieder-oeffnen` nutzen das. Die `UserId`-Felder in den DTOs bleiben (Frontend sendet sie noch), werden aber ignoriert. Beim Bau neuer Endpoints mit Audit/Owner-Feldern: nie `dto.UserId` o.ä. verwenden.
- **Lohn-Beträge server-autoritativ (Walter-Vorgabe 20.05.2026):** `POST /api/payroll/confirm` übernimmt KEINE Geldbeträge mehr aus dem Request-Body. `ConfirmPayroll` ruft intern `Calculate(...)` (read-only, dieselbe Engine wie GET /calculate) auf und speichert AUSSCHLIESSLICH die server-berechneten Werte in `payroll_snapshot` + `payroll_saldo` (Brutto/Netto/SV/QST/Saldi + server-autoritatives `SlipJson`). Die einzige GF-Entscheidung, die der Server nicht selbst ableiten kann, ist die Ferien-Kürzung (Art. 329b OR) — sie kommt als Bool `ConfirmPayrollDto.ApplyFerienKuerzung` und wird mit dem server-berechneten `ferienKuerzung.vorschlagTage` reproduziert (`ferienTageSaldoNeu − vorschlag`). Geldbeträge sind von dieser Entscheidung NICHT betroffen. Die übrigen dto-Betragsfelder bleiben im DTO (Frontend sendet sie noch), werden aber ignoriert. Bei Manipulation wird also der korrekte Server-Wert gespeichert, nicht der gefälschte.
