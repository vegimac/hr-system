2. **Doppelte DOM-IDs.** Bei neuen Komponenten in `index.html` immer prüfen ob die ID schon existiert. Convention: Modul-Prefix benutzen (`stz...`, `ce...`, `vt...`, `pb...`, `qst...`, `ein...`).
   - **Filial-Einstellungen inline (Walter-Vorgabe 14.05.2026):** Der „Einstellungen"-Tab im Filial-Detail (`branches-detail.js`) ist direkt editierbar — Inline-Felder (`ein…`-IDs) + ein „Speichern"-Button (`saveEinstellungen()`), der die 5 PATCH-Endpoints (`nighthours`, `auto-ferien-geld-dezember`, `karenz`, `lgav`, `thirteenth-payouts`) parallel aufruft. Die alten Popup-Modals in `branch-modals.js` (`openNightHoursModal`, `openKarenzModal`, `openLgavModal`, `openAutoFerienGeldModal`, `openThirteenthPayoutsModal` + deren `save…` + Modal-HTML in `index.html`) sind **toter Code** — bewusst erhalten, aber nicht mehr verdrahtet. Das 13.-ML-Monatsraster gibt es doppelt: `tp…` (altes Modal, tot) und `einTp…` (Inline, aktiv) — NIE mischen. **Periodenregel-Modal komplett entfernt** (Walter-Vorgabe 16.05.2026): keine Periodenregel mehr seit Akonto-Lohn-Modell, Lohnperiode = Kalendermonat. „Normale Wochenstunden / Ferien % / Feiertag %" bleiben im Tab nur Anzeige (kein PATCH-Endpoint).
3. **Frontend-Filter nach `companyProfileId`** — MA mit `companyProfileId === null` müssen gehandhabt werden (Legacy-Daten). Filter in `applyEmpFilter` (employees.js) und `loadVtList` (index.html) nutzen Fallback wenn alle Verträge unzugewiesen sind.
4. **Compliance-Check** im Edit-Modal & Vertrags-Import muss vor dem Lohn-Default-Setzen laufen (asynchron — `await runComplianceCheck(idx)` statt `triggerComplianceCheck`). Der Check füllt das Lohnfeld nur, wenn leer ODER unter Mindestlohn.
5. **Mindestlohn-Regel-Lücken in DB** — wenn `status = 'NO_RULE'` aus `/api/compliance/check-live` kommt, fehlt eine Kombi (z.B. FIX-M + SHIFT_LEADER_*) in `minimum_wage_rule_new`. Tabelle hat optional `age_max`-Spalte für altersabhängige Regeln (z.B. CREW + FLEX + Ia + age_max=17 = 16.85 CHF/h für Jugendliche bis zum 18. Geburtstag). **Alter = am letzten Tag des Stichtag-Monats** (Walter 07.10.2026: Geburtstag 30. Juli ⇒ ab 1. Juli Erwachsenen-Mindestlohn) — einzige Stelle `Services/MindestlohnAlter.cs` (Live-Check, Vertrags-Check, Dashboard, Lohn-Check; Tests `MindestlohnAlterTests`), nie eigene Altersrechnung bauen. Vertragsfenster nimmt das Geburtsdatum vom MA des Vertrags (`ceMaZumVertrag`), nie blind `selectedVtEmployee`. Frontend sendet `birthDate` mit, Backend wählt spezifischste Regel via `ORDER BY age_max ASC NULLS LAST`. Compliance-Check fällt für Verträge in der Vergangenheit auf `effectiveDate=heute` zurück (DB hat oft keine alten 2024/2025-Regeln).
6. **DateTime vs DateOnly** — `Employment.ContractStartDate` ist `DateTime`, `PayrollPeriode.PeriodFrom` ist `DateOnly`. Bei Vergleichen mit `DateOnly.FromDateTime(...)` umwandeln.
7. **Stichtag für Lohn-/Compliance-Checks = älteste offene Lohnperiode, NIE `DateTime.Now`** (Walter-Vorgabe 28.05.2026, ABSOLUT). Jede Berechnung, die für den Lohnlauf relevant ist (Mindestlohn-Check im Dashboard, Vertrag-Anpassungs-Vorschau, Compliance-Warnungen), nimmt als „heute" die **ÄLTESTE noch offene Lohnperiode** (`payroll_periode.period_from` mit `status != 'abgeschlossen'`), nicht das Tagesdatum. Bei gefilterter Filiale die Periode dieser Filiale (`WHERE company_profile_id = X`), sonst global die kleinste über alle Filialen. Falls keine offene Periode existiert (alles abgeschlossen): Fallback auf heute. Grund: ein Check soll für den Lohnlauf relevant sein, nicht für den Kalender — z.B. der Mindestlohn-Check muss gegen den Mindestlohn der zu-verarbeitenden Periode greifen, nicht gegen den von heute. Umgesetzt in `DashboardService.cs` (Block „Mindestlohn-Compliance"). Bei neuen Compliance-Endpoints: Stichtag-Helper anwenden, NIE `DateTime.Now`/`DateTime.UtcNow`/`now` direkt im Filter verwenden. Walter-Bug 28.05.2026: das System hatte Zeljka Pajic einen Mindestlohn-Verstoss gemeldet, weil es den 2011er-Vertrag (Crew Trainer 21.50) gegen den heutigen L-GAV (21.66) maß — der aktuelle Vertrag 1.1.2026 ist HOST_CT 21.66 und korrekt. Ursache: 1) Stichtag war `now`, 2) alte Verträge stehen oft fälschlich auf `IsActive=true`. Fix: Stichtag = älteste offene Periode + Datums-Filter (`ContractStartDate ≤ Stichtag AND ContractEndDate ≥ Stichtag`). Datenbereinigung dazu: `migrations-archive/cleanup_old_contracts_inactive.sql` setzt alle Verträge mit `contract_end_date < 2026-01-01` auf `is_active = false`.
8. **Startup-Seeds in `Program.cs` müssen echt idempotent sein.** Guard NIE an eine einzelne fest verdrahtete Sentinel-Zeile hängen (`WHERE NOT EXISTS (… code='KTG' AND valid_from='2026-01-01')`) — wird diese Zeile im UI editiert oder gelöscht, läuft der ganze Seed bei JEDEM Start erneut und erzeugt Dubletten. Richtiges Muster: `WHERE NOT EXISTS (SELECT 1 FROM <tabelle>)` (nur in leere Tabelle seeden, wie beim `lohnposition`-Seed) und zusätzlich ein UNIQUE-Index auf den fachlichen Schlüssel. Für `social_insurance_rate` umgesetzt (Index `ux_social_insurance_rate_natural`, Bereinigung in `migrations-archive/fix_social_insurance_rate_dedup.sql`); SV-Sätze werden im Betrieb über `/api/social-insurance-rates` gepflegt, nicht über den Seed. **Zusatz (Walter-Bug 06.08.2026, dashboard_warning_config):** Start-UPDATEs dürfen NIE an einem Feld guarden, das der User im UI editiert (`WHERE severity_base != 'critical'` zwang Walters «Wichtig»-Einstellung bei jedem Deploy zurück auf Kritisch). Einmal-Migrationen guarden am ALTEN Label/Sentinel (das nach dem ersten Lauf verschwindet); User-editierbare Felder (`enabled`, `severity_*`, `warn_days`, `escalate_days`) werden per Start-Seed grundsätzlich NIE überschrieben — nur via INSERT … ON CONFLICT DO NOTHING in leere Zeilen.

9. **Schema-Stand (Walter-Vorgabe 09.09.2026, ABSOLUT):** Der Start-SQL-Block in `Program.cs` läuft nur, wenn `schema_stand.stand` < `const int SchemaStand` (oben in Program.cs). **Wer im Startblock etwas ergänzt oder ändert — neue Spalte, Tabelle, Index, Seed, UPDATE-Migration — erhöht `SchemaStand` im selben Commit um 1.** Layout/JS/CSS/Controller-Logik: nicht erhöhen. Walter macht das nie selbst; das ist Pflicht des Agenten, der das SQL schreibt. Vergessen ⇒ Schema-Check scheitert, deploy.sh stoppt vor Prod. Seeds fängt der Check NICHT — deshalb auch bei reinen Daten-Seeds erhöhen. **Platzierung (Lehre 21.09.2026, `qst_periodisch`):** jedes `ALTER TABLE … ADD COLUMN` / `CREATE TABLE` muss im Startblock **VOR** dem Aufruf `SchemaCheckService.Pruefe(...)` stehen (Suchanker «Schema-Check läuft IMMER») — steht es dahinter, meldet der Check «fehlende Spalte», deploy.sh bricht vor Prod ab, und der Schema-Stand ist auf Test trotzdem schon gespeichert (dann Stand nochmals erhöhen).

Bei Raw-SQL mit DateTime-Parametern greift die Normalisierung nicht.
