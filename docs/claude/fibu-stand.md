## Fibu-Journal / Kontoplan / Abacus (Walter-Vorgabe 22.05.2026 — in Arbeit)

Ziel: aus dem abgeschlossenen Lohnlauf ein Fibu-Journal erzeugen (wie der heutige Mirus-Export), später ein Abacus-Export. Grundlage ist das Mirus/McDonald's-Schweiz-Buchungsschema, das Walter als `export.xls` (225 Zeilen) geliefert hat.

- **Buchungsmodell (aus den Mirus-Fibujournal-Exporten abgeleitet):** Jede Lohnart wird zu einer Buchungszeile **Soll-Konto / Gegenkonto / Betrag / Text**. Konto hängt ab von **Lohnart (Position+SubPos)** × **Kostenstelle** (= Vertragsmodell: 100 Crew Fix=MTP(/FIX), 200 Crew Flex=FLEX, 300 Management, 400 Gerant). Konto **1920** ist das zentrale Lohn-Durchlaufkonto (Saldo 0). Rückstellungen (Ferien/Feiertage/13.) laufen **zweistufig**: Vormonat auflösen (`is_vormonat=true`, RST→Aufwand) + aktueller Monat bilden (Aufwand→RST) — deckt sich mit unseren Salden Vormonat/aktuell. Sammelkonten: 4062 = AHV+ALV+FAK AG, 2070 = dito Verbindlichkeit; 4060/2080 = BVG; 4061/2090 = BUZ/NBU/KTG; 2010 = QST; 2023 = LGAV; 2071 = Familienzulagen; 2050 = Nettolohn.

  - **Codes-Nachtrag-Wartung (Walter 22.05.2026, amount-preserving):** `POST /api/payroll/refresh-snapshot-codes?companyProfileId&year&month` (admin-only, `RefreshSnapshotCodes` in PayrollController) berechnet jeden Snapshot via `CalculateAsync` NUR als **Code-Quelle** und überträgt per Bezeichnungs-Match ausschliesslich `categoryCode`/`code` auf die bestehenden `abzugLines`/`lohnLines` (`MergeLineCodes`) — der gespeicherte `betrag` bleibt eingefroren. **Nicht** wholesale ersetzen: EnsureAsync (LGAV) committet selbst und ergänzt nachträglich pro MA Beiträge, die seit dem Bestätigen fehlten; ein wholesale-Replace würde diese frischen Beträge in den eingefrorenen Snapshot sickern lassen → Durchlaufkonto 1920 ginge nicht auf (Bug 22.05.2026: LGAV 2'123.94 eingefroren vs. 2'970 frisch → 1920 +846.06). Setzt nur Codes auf Zeilen, die noch KEINEN haben (idempotent; eine bereits wholesale-überschriebene Periode heilt sich NICHT von selbst → Reset + neu bestätigen). Status/Saldi/Workflow unangetastet. Frontend: `payroll.js → lohnRefreshCodes()`, Button „🔄 Codes nachtragen" in `_lohnWfRenderStatusBar` (nur Rolle `admin`, ab `provisorisch_abgeschlossen` + `abgeschlossen`). Hinweis: NEU bestätigte Perioden tragen die Codes ohnehin nativ (Engine taggt beim Berechnen) — der Knopf ist nur für Alt-Perioden.
  - **LGAV-Code = Mirus-Position 600.24 (Walter 22.05.2026):** Die LGAV-Lohnposition trug fälschlich Code „140" → traf keine Kontoplan-Zeile, alle LGAV-Abzüge wurden im Journal übersprungen (1920 ging um die LGAV-Summe nicht auf). Fix: `lohnposition.code` 140 → **600.24** (= Kontoplan-Position, Soll 1920 / Gegen 2023), `LgavBeitragService.LgavCode` parallel auf „600.24". Lehre: für JEDEN Lohnpos-Abzug muss `lohnposition.code` EXAKT der Mirus-Kontoplan-Position (Position.SubPos) entsprechen, sonst wird die Zeile übersprungen. Verbleibende Kandidaten mit potenziell abweichendem Code (130/131 GastroSocial Uno, 210 Diverse, 65/75 Korrektur) — nur relevant falls sie als Abzug auftauchen; bei Bedarf gleich angleichen.
  - **Familienzulagen liegen AUSSERHALB des Journal-Netto (Walter 22.05.2026, Diagnose-Lehre):** `snapshot.Netto = nettolohn = Round05(totalLohn + totalAbzuege)` (PayrollCalculationService Z.195) und enthält **NICHT** `zulagenExtraTotal` — Familienzulagen/Spesen kommen erst im `auszahlungsbetrag` dazu (Z.267). Das Journal bucht `snapshot.Brutto`/`snapshot.Netto`, also balanciert es per Identität `Brutto = Netto + Abzüge`, unabhängig von FamZ. **Konsequenz:** FamZ dürfen im aktuellen Journal NICHT auf 1920 gebucht werden (sonst Überschuss). Eine kurzzeitig gebaute FamZ→2071-Buchung wurde wieder ENTFERNT. Mirus-konform (auszahlungsbetrag inkl. FamZ als Netto/2050 **und** FamZ → 2071/1920) ist als **v3** offen.
  - **1920-Differenz war LGAV-Inflation, NICHT FamZ (Walter 22.05.2026):** Die Test-Periode Januar zeigte +846.06 auf 1920. Ursache: der ERSTE (wholesale) `RefreshSnapshotCodes` hat die `abzugLines` komplett ersetzt und dabei das via EnsureAsync nachträglich vervollständigte LGAV (2'970) in den Slip geschrieben, während der eingefrorene `snapshot.Netto` noch mit dem Bestätigungs-LGAV (2'123.94) gerechnet war. Diagnose-Formel: 1920-Differenz = `Σ abzugLines − (ΣBrutto − ΣNetto)`. Wenn ≠ 0 → Slip-Abzüge stimmen nicht mit dem eingefrorenen Netto überein → Periode zurücksetzen + neu bestätigen (regeneriert konsistente Snapshots mit nativen Codes). **Lehre:** zuerst `ΣBrutto − ΣNetto` gegen `Σ abzugLines` prüfen, BEVOR man eine fehlende Buchungsart vermutet. Der amount-preserving Merge (jetzt aktiv) verhindert künftige Inflation. **Hinweis:** AG-Sozialbeiträge (4060/4061/4062) und Ferien/Feiertag-RST berühren Konto 1920 NICHT. **Noch offen (v2/v3):**
  - **RST Ferien/Feiertage (Walter 22.05.2026, Tagessatz präzisiert 26.05.2026):** `FibuJournalService` bucht den monatlichen NETTO-Zuwachs (Accrual − Bezug) pro MA → Kontoplan **4070.20** (Ferien) / **4070.30** (Feiertag), Aufwand 4000/4001/4055 ↔ RST-Konto **2019** (positiv = bilden, negativ = auflösen, S/H getauscht). **Tagessatz FIX/FIX-M = Monatslohn × 12 / 365** (Kalenderbasis — fester Monatslohn unabhängig von der Anzahl Tage). KEIN /364 mehr — die frühere 1/7-Formel galt nur für MTP (Stundenlöhner). Damit identisch zu `PayrollCalculationEngine.fixTagessatz`. Pro Modell: **FIX/FIX-M** Tage × Tagessatz; **FLEX/MTP** Ferien als CHF aus dem Ferien-Geld (`ferienGeldAccrual − ferienGeldAuszahlung`, kein Tagessatz); **Feiertag** nur FIX/FIX-M (andere haben 0 Feiertag-Tage). Quelle = SlipJson-Felder `ferienTageAccrual/Genommen`, `feiertagTageAccrual/Genommen`, `ferienGeldAccrual/Auszahlung`; Employment-Lohn für den Tagessatz. **WICHTIG:** diese RST-Buchungen berühren Konto 1920 NICHT (Aufwand ↔ RST) → können das Durchlaufkonto nie aus der Balance bringen.
