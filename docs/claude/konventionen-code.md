- **QuestPDF: Row-Breiten nachrechnen (Bewerbungsbogen-Bug 13.08.2026).** Eine `Row` mit `AutoItem`/`ConstantItem`-Summe > Blattbreite (~495pt bei A4, 1.5cm Rand) wirft zur LAUFZEIT `DocumentLayoutException: conflicting size constraints` — die Meldung nennt KEINE Stelle. Klassiker: zwei lange Frage-Texte + Checkboxen in EINER Zeile, oder Ziffern-Boxen (ConstantItems) in einer zu schmalen RelativeItem-Spalte. Bei solchen Fehlern zuerst Breiten prüfen (Fix: Zeile aufteilen oder Box-Gruppe als `AutoItem`), nicht die Seitenhöhe.

- **NIE geschweifte Klammern in `ExecuteSqlRaw`-SQL (Walter-Crash 13.08.2026, ABSOLUT).** EF Core jagt den SQL-String durch `String.Format` — ein `DEFAULT '{}'` o.ä. wirft zur LAUFZEIT beim Serverstart `FormatException: Expected an ASCII digit` → Startup-Crash/Restart-Loop (Produktion down; konkret: `lse_version.config_json DEFAULT '{}'`). Regel: in Start-Migrations-SQL Klammern entweder als `{{` / `}}` escapen (Muster `slip_json JSONB NOT NULL DEFAULT '{{}}'`) oder den Default weglassen und im EF-Model setzen. JSON-Seeds NIE als Raw-SQL, sondern via EF + `JsonSerializer.Serialize`. Zweite Lehre desselben Vorfalls: **EF-Seeds laufen in DATEIREIHENFOLGE von Program.cs** — ein Seed, der eine Tabelle liest, muss NACH deren `CREATE TABLE`-Block stehen (der LSE-Seed stand davor → «relation does not exist» beim Erst-Start).

- **NIEMALS ein ASCII-`"` (U+0022) innerhalb eines C#-Strings verwenden — wiederkehrender Build-Bug (Walter-Vorgabe 04.07.2026, ABSOLUT).** In deutschen Texten sieht das typografische Paar `„…"` optisch korrekt aus, aber das SCHLIESSENDE Zeichen ist oft ein ASCII-`"` (U+0022) und beendet dann den C#-String vorzeitig → Dutzende Folge-Syntaxfehler (CS1003/CS1002/CS1010 „Zeilenvorschub in Konstante" usw.). **Regel:** in C#-String-Literalen (`"..."`, `$"..."`) für Anführungszeichen um einen Wert IMMER **Guillemets** `«…»` (U+00AB/U+00BB) verwenden — die sind kein String-Delimiter und immer sicher. Beispiel: `$"Typ «{code}» wird verwendet."` — NIE `$"Typ „{code}\" …"`. Gilt für alle Fehlermeldungen, Logs, PDF-/Postfach-Texte. In Kommentaren (`//`) sind die typografischen Zeichen unkritisch (werden nicht geparst). Nach jeder C#-Edit mit deutschem Text kurz prüfen, dass kein blankes `"` mitten im String steht.

- **SQL-Migrationen immer für TablePlus liefern.** Walter führt SQL direkt in TablePlus aus (nicht via `psql` CLI). Daher: reinen SQL-Block geben, kein `psql -d hr_system -U postgres -f ...` Wrapper, keine `\d`/`\i`-Meta-Kommandos. Die `.sql`-Datei in `migrations-archive/` darf den Wrapper-Kommentar als Doku enthalten, aber im Chat antworte ich mit dem reinen SQL zum Copy-Paste.

- **Zeitstempel IMMER in Lokalzeit schreiben — `DateTime.Now`, NIE `DateTime.UtcNow` (Walter-Vorgabe 30.06.2026).** Die `timestamp`-Spalten der DB sind durchgängig **`timestamp without time zone`**. Npgsql weigert sich, einen `DateTime` mit `Kind=Utc` dorthin zu schreiben (Fehler „Cannot write DateTime with Kind=UTC to PostgreSQL type 'timestamp without time zone'"). Also: für alle `created_at`/`geaendert_am`/Audit-/Log-Zeitstempel `DateTime.Now` (Kind=Local) verwenden — auch im Model-Default (`public DateTime CreatedAt { get; set; } = DateTime.Now;`) UND bei jeder expliziten Zuweisung. Beim Mapping neuer `DateTime`-Felder die Spalte als `timestamp without time zone` führen (`.HasColumnType("timestamp without time zone")`) und nie UTC-Werte hineinschreiben. (Konkret aufgetreten beim `employment_probation_log.created_at`.)

- **Datum/Zeit-Regelwerk (Walter-Vorgabe 13.07.2026, ABSOLUT — «für immer merken», das Problemfeld traf uns mehrfach):**
  1. **`DateOnly.FromDateTime` / `TimeOnly.FromDateTime` NIE in EF-SQL-Projektionen** (`.Select(...)` vor `ToListAsync`) auf `date`-Spalten — Npgsql kann das nicht übersetzen und wirft zur LAUFZEIT «Can only apply TimeOnly.FromDateTime on a timestamp or timestamptz column» (HTTP 500; konkret: QST-Vorschlag-Endpoint, Kinder-Abfrage 13.07.2026). Muster: Felder ROH laden (`Select(f => new { f.Feld1, … })` + `ToListAsync()`), DANACH im Speicher konvertieren. Solche Fehler tauchen erst beim Aufruf auf, nicht beim Build — bei jeder neuen EF-Projektion mit Datums-Konvertierung daran denken.
  2. **Zeitstempel lokal** (`DateTime.Now`, nie `UtcNow`) — siehe Konvention 30.06.2026 oben (`timestamp without time zone`).
  3. **★★★ easy@work = UTC, UI = Zürich — NIEMALS Roh-Timestamps als Kalendertag nehmen (Walter 26.07.2026, ABSOLUT, mehrfach schiefgegangen):** Jeder easy@work-`from`/`to`-String (`"yyyy-MM-dd HH:mm:ss"`) ist UTC. Mitternacht Zürich = oft `22:00`/`23:00` UTC des **Vortags**. **IMMER** `EawDateUtil.ParseSwissDate` (UTC→Europe/Zurich). Zusätzlich: Custom-Field-Intervall-«to» speichert easy **inkonsistent** (mal inklusives Bis als Zürich-00:00 des Tages, mal exklusives Mitternacht = nächster Tag 00:00). Deshalb:

ENDE **NIEMALS** aus easy-«to» übernehmen — IMMER selbst rechnen: `Employee.NightWorkValidUntil` = Beginn + 2 Jahre − 1 Tag (ab Alter 45 am Ausstellungstag: + 1 Jahr − 1 Tag). easy-«to» nur prüfen mit `EawDateUtil.IntervalEndMatchesSoll` (beide Lesarten); bei Abweichung Flag `night_work_exam_easy_mismatch` + Chip/ToDo.      - **Vertrag + Lohnsatz «Bis» = Zürcher Kalendertag (Walter-Vorgabe 24.09.2026, ERSETZT die «inklusive Mitternacht» vom 22.09.):** easy schreibt «Bis» mal als 23:59:59, mal als 00:00 Zürich — beide meinen den Tag, den die Spalte «Bis» in easy zeigt. **00:00 ist NICHT der Vortag.** `EawContract.To` und `EawPayRate.To` lesen deshalb wie «Von» mit `ParseSwissDate` (UTC → Zürich → Kalendertag; leer = kein Ende) — NIE mit `ParseSwissInclusiveEndDate` (der Abzug war unser Fehler; die Methode bleibt nur für Absenzen/Nachtarbeit/Custom-Fields).
